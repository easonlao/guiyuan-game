# 归元弈 (Guiyuan) - 技术可行性与架构演进研究报告 (FSR)

**评估对象：** 规则引擎、无头仿真系统、客户端 AI、跨端解耦与多形态演进路线

---

## 1. 项目研发背景与演进路径 (Project Background & Evolution)

《归元弈》项目采取了典型的 **Code-First（代码先行试错，随后顶层抽象固化）** 研发路径：
1.  **阶段起步（Web 验证原型）**：前期使用原生 JavaScript、Vite 和 DOM/CSS 快速构建了双人博弈与基础视听，并接入 Supabase 探索了联机对战雏形（该阶段资产已归档于 `legacy/`）；
2.  **深度推进（无头仿真与数值平衡）**：为了彻底攻克“五行相生相克与阴阳流转”的数值平衡难题，工程团队构建了完备的无头自动化对弈系统（`HeadlessMatch`、`ExperimentRunner`），成功基于成千上万场自博弈跑通了规则平衡；
3.  **当前阶段（架构解耦与跨端落地）**：在核心规则与数值模型得到充分验证后，完成架构脱水——核心逻辑已抽离为环境无关的 TypeScript 纯函数/状态库（`src/core/`），以**“微信小游戏纯单机版”**（纯 TS Canvas 2D，ADR 0004）作为首个商业化 MVP 落地，同时保留未来向跨端联网演进的能力。

本文档系统论证该技术路线的可行性、风险边界及成本效益。

---

## 2. 核心技术可行性论证 (Technical Feasibility)

### 2.1 规则引擎与状态确定性可行性 (Deterministic Engine) —— **已完全验证 (100%)**
*   **论证依据**：现有的 `TurnManager`、`ActionResolver` 和 `State` 均基于纯状态流转设计，不依赖任何不可控的外部异步时序或 UI 状态。
*   **验证结论**：通过基于 PRNG 种子的无头对战（`HeadlessMatch` + `baseSeed`），系统已证明在给定相同初始种子和玩家决策序列下，整局对局的动作解析、状态转移、计分结算能够达到 **100% 确定性回放**。这为跨平台移植、离线测试与后续网络对战的状态校验奠定了坚实基础。

### 2.2 仿真驱动的数值平衡可行性 (Data-Driven Balance) —— **极高可行性 (Demonstrated)**
*   **论证依据**：五行博弈包含吸纳、调息、化、破及爆发动作，规则交互维度高，传统人工对战测试难以收敛数值平衡。
*   **验证结论**：项目中已落地运行的 `ExperimentRunner`、`CandidateValidation` 与各实验脚本证明：
    *   单局纯逻辑无头对战耗时在亚毫秒级（性能预算与实测基线见 `docs/SRS.md` §4.2）；
    *   AI 能够在几秒钟内完成千场对弈，输出精准的胜率分布、先手优势度、终局归元达成率与得分分布；
    *   基于代码的自博弈完全具备持续迭代游戏数值的能力，大幅缩减后续版本调优成本。

### 2.3 移动端/轻量端 AI 算力可行性 (Edge AI Feasibility) —— **完全可行且具备弹性对策**
*   **现状评估**：现有的 AI 基于多维度启发式评估（`ActionEvaluator` 按 `StrategyWeights` 权重打分，`Strategy` 选择预设模板），单次决策主要进行动作打分与状态预测，计算复杂度为 $O(N)$（$N$ 为当前可用动作候选数，通常 $\le 10$）。
*   **执行耗时**：实测单次决策在普通 CPU 下耗时 $< 2\text{ms}$，远低于移动端 60FPS 要求的 `16ms` 阈值。
*   **降级/弹性预案**：
    *   在接口层预先定义异步契约（工程方案见 `docs/HLD.md` §2）；
    *   若后续引入更深层的蒙特卡洛树搜索（MCTS）或局部前瞻算法，可无缝利用微信小游戏原生的多线程 `Worker` 进行后台计算，彻底杜绝主线程卡顿掉帧。

### 2.4 跨端解耦与表现层接入可行性 (Decoupled View Porting) —— **极高 (High)**
*   **解耦现状**：核心逻辑层（`src/core/`）与表现层（`src/minigame/`）、存储适配层（`src/adapters/`）边界清晰（强制手段见 `docs/HLD.md` §4.2）。业务逻辑完全不依赖 `document`、`window` 等 DOM 专属接口。
*   **表现层适配性**：
    *   当前表现层为纯 TypeScript + Canvas 2D（`wx.createCanvas()`），零第三方引擎依赖（ADR 0004），WSL 命令行即可开发调试；
    *   迁移/扩展方式：表现层仅通过 `TurnManager` 的公开 API 与 `EventBus` 消费核心状态，替换渲染层不影响任何计算逻辑；
    *   若未来需要更重的渲染引擎，须按 ADR 0004 重新评估并另立决策，当前不引入引擎。

### 2.5 存储与网络降级/升级可行性 (Storage & Network Versatility) —— **完全可行**
*   **脱机单机降级（MVP 策略）**：
    *   已落地通用的存储适配层，将原先发往 Supabase 的读写请求重定向至本地持久化接口（接口与各环境实现见 `docs/HLD.md` §2 Layer 2）。
    *   能够以 **0 服务器成本** 极速交付首个稳定商业版本。
*   **联机功能储备（远期演进）**：
    *   旧 JS 原型中已存在 `RoomManager`、`SimplifiedPVPManager` 和断线重连逻辑，现归档于 `legacy/src/network/`，可作为协议与交互设计参考；
    *   当单机版验证市场成功后，可基于其设计重建网络适配层，实现多人联机对战。

## 3. 研发与经济成本评估 (Economic & Resource Feasibility)

| 维度 | MVP 阶段 (单机小游戏) | 扩展阶段 (跨端联机) | 可行性结论 |
| :--- | :--- | :--- | :--- |
| **服务器/带宽成本** | **0 元** (纯客户端脱机运行) | 阶梯式 (基于 Supabase 免费额度/低成本 BaaS) | 资金风险极低 |
| **引擎与开发工具** | **0 元** (零引擎依赖：纯 TS + Canvas 2D，VSCode/oxc 开源) | 同左 | 零工具采购成本 |
| **平台资质与审核** | 微信小游戏个人主体免费注册，提审周期快 | 需考虑软著与联网合规资质 | 先单机后联机路径合规阻力最小 |
| **研发效能 (AI-First)** | 核心逻辑由 AI 驱动测试并快速重构，人工只需处理 UI 摆放 | 前后端契约复用 | 研发周期可压缩 60% 以上 |

## 4. 关键风险矩阵与应对策略 (Risk Assessment)

| 风险类别 | 风险描述 | 影响级别 | 预防与应对措施 |
| :--- | :--- | :---: | :--- |
| **性能风险** | 低端机型上 AI 决策或复杂粒子特效引起掉帧 | 中 | 1. 严格约束单帧逻辑计算 $<16\text{ms}$；<br>2. 预留 Worker 异步线程架构；<br>3. Canvas 2D 动效（场景树 + 补间引擎）支持分级降级配置。 |
| **包体超标风险** | 微信小游戏要求首包体积 $\le 4\text{MB}$ | 高 | 1. 纯 TS 逻辑库经 Terser 压缩后通常 $<200\text{KB}$；<br>2. Vite/Terser 打包压缩，无引擎运行时开销；<br>3. 音效与高精度美术资源走远程分包加载。 |
| **单机数据安全** | 微信缓存清理导致本地存档丢失，纯前端计算易作弊 | 低 | 1. MVP 阶段重在玩法体验，弱化作弊顾虑；<br>2. 存档接入微信原生用户数据加密，后续可无缝迁移至微信云开发。 |
| **架构腐化风险** | 迭代过程中 UI 代码与核心逻辑重新产生双向耦合 | 高 | 引入依赖防腐巡检作为 CI 硬卡点（手段见 `docs/HLD.md` §4.2），严格禁止表现层逆向侵入逻辑层。 |

## 5. 全生命周期技术路线图 (Evolution Roadmap)

各阶段的**交付范围、时点与验收标准**归 `docs/SRS.md` §5，本节不复制。从可行性与成本角度看，演进路径可归纳为四步：

| 阶段 | 主题 | 对成本 / 风险的意义 |
| :--- | :--- | :--- |
| Phase 1（已完成） | Web 原型与规则打通 | 以最低成本验证规则与确定性边界 |
| Phase 2（已完成） | TS 纯逻辑库与防腐工具链 | 把数值平衡变成可自动化的问题，摆脱人工试错 |
| Phase 3（进行中） | 纯 TS Canvas 微信小游戏 MVP | 0 服务器成本交付首个商业版本 |
| Phase 4（远期） | 跨平台多人联机 | 复用 Phase 1 网络层设计，仅在市场验证后投入 |

---
*结论：本项目的核心规则、算法与跨端分层方案在理论与工程实践上均高度可行。以 TS 纯逻辑库为基石、以小游戏为跳板、保留联机扩展能力的演进路线是兼顾低成本与高扩展性的最优技术路径。*
