# 归元弈 (Guiyuan) - 技术可行性与架构演进研究报告 (FSR)

**文档版本：** V2.0 (全项目技术演进基准)  
**评估对象：** 规则引擎、无头仿真系统、客户端 AI、跨端解耦与多形态演进路线  

---

## 1. 项目研发背景与演进路径 (Project Background & Evolution)

《归元弈》项目采取了典型的 **Code-First（代码先行试错，随后顶层抽象固化）** 研发路径：
1.  **阶段起步（Web 验证原型）**：前期使用原生 JavaScript、Vite 和 DOM/CSS 快速构建了双人博弈与基础视听，并接入 Supabase 探索了联机对战雏形；
2.  **深度推进（无头仿真与数值平衡）**：为了彻底攻克“五行相生相克与阴阳流转”的数值平衡难题，工程团队构建了完备的无头自动化对弈系统（`HeadlessMatch`、`BatchComparison`、策略锦标赛），成功基于成千上万场自博弈跑通了规则平衡；
3.  **当前阶段（架构解耦与跨端落地）**：在核心规则与数值模型得到充分验证后，启动架构脱水工程——将核心逻辑库彻底抽离为环境无关的 TypeScript 纯函数/状态库，以**“微信小游戏纯单机版”**作为首个商业化 MVP 落地，同时保留未来向跨端联网演进的能力。

本文档系统论证该技术路线的可行性、风险边界及成本效益。

## 2. 核心技术可行性论证 (Technical Feasibility)

### 2.1 规则引擎与状态确定性可行性 (Deterministic Engine) —— **已完全验证 (100%)**
*   **论证依据**：现有的 `GameEngine`、`ActionResolver` 和 `StateManager` 均基于纯状态流转设计，不依赖任何不可控的外部异步时序或 UI 状态。
*   **验证结论**：通过 `SeededMatch`（基于 PRNG 种子的无头对战），系统已证明在给定相同初始种子和玩家决策序列下，整局 30 大回合（60 次行动机会）的动作解析、状态转移、计分结算能够达到 **100% 确定性回放**。这为跨平台移植、离线测试与后续网络对战的状态校验奠定了坚实基础。

### 2.2 仿真驱动的数值平衡可行性 (Data-Driven Balance) —— **极高可行性 (Demonstrated)**
*   **论证依据**：五行博弈包含吸纳、调息、化、破及爆发动作，规则交互维度高，传统人工对战测试难以收敛数值平衡。
*   **验证结论**：项目中已落地运行的 `BatchComparison` 和实验脚本（如攻防数值扫描、爆发稀有度削弱实验）证明：
    *   单局纯逻辑无头对战耗时在 **微秒到毫秒级**；
    *   AI 能够在几秒钟内完成千场对弈，输出精准的胜率分布、先手优势度、终局归元达成率与得分分布；
    *   基于代码的自博弈完全具备持续迭代游戏数值的能力，大幅缩减后续版本调优成本。

### 2.3 移动端/轻量端 AI 算力可行性 (Edge AI Feasibility) —— **完全可行且具备弹性对策**
*   **现状评估**：现有的 `AIController` 基于多维度启发式评估网络（`ActionValueCalculator` + `UnityEvaluator` + `StrategySelector`），单次决策主要进行动作打分与状态预测，计算复杂度为 $O(N)$（$N$ 为当前可用动作候选数，通常 $\le 10$）。
*   **执行耗时**：实测单次决策在普通 CPU 下耗时 $< 2\text{ms}$，远低于移动端 60FPS 要求的 `16ms` 阈值。
*   **降级/弹性预案**：
    *   在接口层预先定义异步契约 `Promise<Action>`；
    *   若后续引入更深层的蒙特卡洛树搜索（MCTS）或局部前瞻算法，可无缝利用微信小游戏原生的多线程 `Worker` 进行后台计算，彻底杜绝主线程卡顿掉帧。

### 2.4 跨端解耦与 Cocos 引擎接入可行性 (Decoupled Engine Porting) —— **极高 (High)**
*   **解耦现状**：核心逻辑层（`src/js/logic/`、`src/js/state/`）与旧渲染层（`src/js/ui/`、`src/css/`）边界清晰。业务逻辑完全不依赖 `document`、`window` 等 DOM 专属接口。
*   **引擎适配性**：
    *   目标引擎 **Cocos Creator 3.x (3.8 LTS)** 原生采用 TypeScript，具备完善的 2D 渲染管线；
    *   迁移方式：将脱水后的纯 TS 逻辑库放置于 Cocos 项目的 `assets/scripts/logic/`，通过事件总线（EventBus）与 Cocos 组件绑定；
    *   该方案已被行业内众多商业化小游戏广泛验证，技术断层为零。

### 2.5 存储与网络降级/升级可行性 (Storage & Network Versatility) —— **完全可行**
*   **脱机单机降级（MVP 策略）**：
    *   当前已规划通用的 `IStorageManager` 适配层。将原先发往 Supabase 的读写请求重定向至本地持久化接口（Node 环境用内存 Mock，微信环境用 `wx.setStorageSync`）。
    *   能够以 **0 服务器成本** 极速交付首个稳定商业版本。
*   **联机功能储备（远期演进）**：
    *   代码库中已存在 `RoomManager`、`SimplifiedPVPManager` 和断线重连逻辑；
    *   当单机版验证市场成功后，可无缝重新激活网络适配层，实现多人联机对战。

## 4. 关键风险矩阵与应对策略 (Risk Assessment)

| 风险类别 | 风险描述 | 影响级别 | 预防与应对措施 |
| :--- | :--- | :---: | :--- |
| **性能风险** | 低端机型上 AI 决策或复杂粒子特效引起掉帧 | 中 | 1. 严格约束单帧逻辑计算 $<16\text{ms}$；<br>2. 预留 Worker 异步线程架构；<br>3. Cocos 粒子与动效支持分级降级配置。 |
| **包体超标风险** | 微信小游戏要求首包体积 $\le 4\text{MB}$ | 高 | 1. 纯 TS 逻辑库经 Terser 压缩后通常 $<200\text{KB}$；<br>2. Cocos 构建时剔除 3D 及物理引擎等无用模块；<br>3. 音效与高精度美术资源走远程分包加载。 |
| **单机数据安全** | 微信缓存清理导致本地存档丢失，纯前端计算易作弊 | 低 | 1. MVP 阶段重在玩法体验，弱化作弊顾虑；<br>2. 存档接入微信原生用户数据加密，后续可无缝迁移至微信云开发。 |
| **架构腐化风险** | 迭代过程中 UI 代码与核心逻辑重新产生双向耦合 | 高 | 引入 **dependency-cruiser** 作为 CI/巡检硬卡点，严格禁止表现层逆向侵入逻辑层。 |
