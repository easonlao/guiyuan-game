# CI：快链自动跑验收，全量突变测试里程碑手动触发，不挂定时

仓库引入 GitHub Actions 时，把「每次推送自动跑什么」与「全量突变测试怎么触发」一次定下：**快链（`npm run verify`）在 PR 与推送到 main 时自动跑**，改动文件的突变测试（`mutation:changed`）作为**观察项**并行跑、只落盘不当门禁；**全量突变测试 + 棘轮对比只能手动触发**（`workflow_dispatch`，对应 `npm run mutation:milestone`）；**不挂 `on: schedule`**。

## 背景与问题

仓库是 public，Actions 分钟数不限量，所以「贵不贵」不是判据。真正的约束是门禁的形状：本仓库的突变测试门禁是**差分棘轮**（`docs/MUTATION-TESTING.md` §3.1）——它只报**基线之外**的新增存活/无覆盖。代码没变、测试没变，存活集合就不变。**没有 diff 的跑法在定义上产不出新发现**，定时跑因此是结构性冗余，不是省不省钱的问题。

同时，快链能跑的验收有明确边界：`npm run verify` 是秒到十几秒级的静态检查 + 类型检查 + 单元测试，适合每次推送；全量突变测试耗时较长（见 `docs/MUTATION-TESTING.md`），只能当里程碑。

## 决定

1. **快链自动**：PR 与推送到主分支时自动跑验收（`npm run verify`），失败即红；改动文件的突变测试作为**观察项**并行跑，红了不阻断验收、只落盘。
2. **全量突变测试 + 棘轮只能手动触发**：不挂 `schedule`，也不挂每次推送。理由就是背景里的那条——门禁是差分棘轮，没有 diff 的跑法在定义上产不出新发现。
3. **观察项不能当门禁**：子集报告做不了棘轮对比（`mutation:check` 识别并退 `2`），所以 `mutation:changed` 在快链里只落盘、不设红线。
4. **触发者写进 `AGENTS.md`**：需求方不是开发者、不会去按按钮，全量那条的实际触发者只能是 agent；「每个 spec 收尾时跑全量 + 棘轮」这条责任落在 `AGENTS.md`，入口是命名脚本 `npm run mutation:milestone`。
5. **流水线里只调命名脚本**：CI 的失败信号只有一个来源——那条命名脚本本身；yaml 里不写裸检查命令，也不设 CI 专属断言（沿用参考仓库 `model-war` 的 ADR-0010 口径；那个编号是它的，不是本仓库的 `docs/adr/0010`）。

具体到哪个 workflow 文件、权限怎么收、观察项的基线 ref 怎么取，是工程方案，归 `docs/HLD.md` §4.5。

## 被否决的方案

- **全量突变测试挂定时（`on: schedule`）**：门禁是差分棘轮，没有 diff 的定时跑在定义上产不出新发现。挂上去只会定期产出一份和基线一样的结果，或把等价突变体的负载抖动误报成信号。
- **全量突变测试挂每次推送**：同上没有 diff，且全量耗时较长、会拖垮每次推送的反馈。
- **把 `mutation:changed` 当快链门禁**：子集报告不能做棘轮对比（`mutation:check` 退 `2`），当门禁只能靠「有没有存活」这种没有基线的口径，等于换掉门禁定义。
- **只删定时、不写触发责任**：删掉定时后，仓库最强的一道门禁将无人触发。故必须同时把触发者写进 `AGENTS.md` 并给命名脚本。

## 后果

- 每次推送的反馈保持在分钟级以内；最强的棘轮门禁没有流水线兜底，其「红」的唯一消费者是跑它的 agent——这条责任落在 `AGENTS.md`。
- 观察项与门禁的区别在流水线里是显式的：观察项用 `continue-on-error` 只落盘，门禁用退出码判红。不会出现「观测项红了」被当成「门禁绿了」，反之亦然。

## 勘误

- （2026-10-15）决定 4 里的「每个 spec 收尾时跑全量 + 棘轮」收窄为：**只在基线最后一次刷新之后 `src/core/logic/**` 有改动时才跑**。理由不是省时间，而是定义——突变体只存在于 `mutate` 覆盖的那个目录，目录未变则存活集合不变，全量在定义上产不出新发现。触发者仍是 agent，这条责任不变。条件、判定命令与已知偏差见 `docs/MUTATION-TESTING.md` §2.2。
- （2026-10-18）`.github/workflows/mutation-milestone.yml` 已删除。决定 2 的「全量 + 棘轮只能手动触发」不变，删掉的是「在 CI 上手动」这个入口。

  该 workflow 从未在 CI 上成功跑过，第一次真正触发就暴露两处故障：dry run 里一条重仿真用例在插桩后被 Vitest 默认的 5s `testTimeout` 打断（`Stryker` 直接放弃）；修掉之后，全量在托管 runner 上跑 118 分钟才到 90%，折合全程约 132 分钟，被当时的 `timeout-minutes: 120` 取消。本地同一份配置约 50 分钟。

  判断依据是决定 4：棘轮的唯一消费者是跑它的 agent，流水线兜不兜底都不改变谁读这份报告。CI 那一份换来的只有「产物可下载」，代价是每条两三小时的等待，以及维护一个从未绿过的配置。全量因此固定走本地 `npm run mutation:milestone`，工程现状见 `docs/HLD.md` §4.5。

- （2026-10-18，同日续）快链里的 `mutation:changed` **观察项**也删掉了，CI 现在只剩 `npm run verify` 一条 job。

  决定 3 说的是「观察项不能当门禁」——这条仍然成立，但反过来说也成立：一个从不当门禁、红了不阻断、产物是 `artifacts/` 里一份没人会下载的报告的 job，实际贡献是每次推送 17 秒与一条 artifact 链接。而突变结果跨环境不可比（同一突变体在 Killed / Timeout 之间随负载翻转，见 `stryker.config.json` 的 `_timeoutComment`），在托管 runner 上跑出来的子集报告比本地更没有参考价值。

  后果一栏里「观察项与门禁的区别在流水线里是显式的」这句自此不再描述任何现存 job——流水线里已经没有观察项。`mutation:changed` 本身仍在 `package.json`，只是改为由 agent 在本地按需跑（`docs/MUTATION-TESTING.md` §1 的表）。工程现状见 `docs/HLD.md` §4.5。
