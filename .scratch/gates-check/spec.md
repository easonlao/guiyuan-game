# Spec: 门禁自检——在当前状态下跑一遍全部门禁 (gates-check)

## Problem Statement

2026-10-25 我写出过一个「每轮必红」的门禁：`check:delivery` 的断言③ 数不可达提交，超过 479 就报警。可 squash / rebase 每轮都抛弃原始提交，那个数只涨不跌——它在真实仓库里**一直是红的**。当时没人发现，因为我只在交付那一刻跑它，看到红就按脚本提示重钉基线，从没停下来问「它凭什么以后能变绿」。

同类还有一次：断言③ 换代时只上树判据，实测 34 个命中、33 个假阳性——也是在真实状态下就是红的。

后来做 `check:facts` 时补上了「门禁还在快链里」这类断言，但那是**逐条手写**的，覆盖不到「某个门禁在当前状态下整体是红的」。

## 决定

1. **自动发现，不列清单。** 扫 `scripts/check-*.mjs` 现场发现（排除自己，否则递归）。列清单会漂：加了新门禁忘了登记，自检就漏掉它。
2. **跑默认参数，要求退出 0。** 抓的是「状态漂移」，不是「参数用法」。
3. **不进 `check:quick`。** 它要跑完全部门禁（含 `git fsck` 与产物构建），比秒级快链重得多。放在交付收尾：那一刻正该确认整套门禁在这个仓库上是否真的都绿。
4. **在 worktree 里跑时说清哪条未受检。** `check-delivery` 的断言④ 数 worktree 数量（收尾后应当只剩主 checkout），在 worktree 里必然红——那不是它坏了。此时给它实际数量，让①②③ 仍被自检到，并明说④未受检。

## 它和「新门禁红过一次」互补

| 方向 | 由谁管 |
|---|---|
| 永远绿的门禁（拦不住东西） | 新门禁必须在自己造的破坏上红一次（§6.3 与 AGENTS.md 四问） |
| 永远红的门禁（没人愿意跑） | 本票的 `check:gates` |

两个方向都得有，单靠一个只堵半边。

## Out of Scope

- 给每个门禁写 `--probe`（自造破坏、必须判红）。那是「永远绿」那一半，本票只做「永远红」这一半。
- 把 `check:gates` 挂进 `check:quick` 或 `verify`。
- 自动修复红掉的门禁：只报告。
