# 01: check:gates——在当前状态下跑一遍全部门禁

**Type:** task
**Blocked by:** None
**Status:** resolved
**Slice:** S1

**What to build:** `scripts/check-gates.mjs` + `npm run check:gates`，挂进交付收尾。

## 行为

1. 扫 `scripts/check-*.mjs` 自动发现门禁（排除自己）。
2. 逐个以默认参数跑一遍，逐个打印绿/红。
3. 有红的 → 列出该门禁最后一行输出，并提示先问「它凭什么以后能变绿」，退出 1。
4. 全绿 → 打印「N 个门禁在当前状态下全部是绿的」，退出 0。

## 三条范围决定

- **自动发现**而不是列清单：清单会漂（新门禁漏登记）。
- **不进 `check:quick`**：要跑 `git fsck` 与产物构建，比秒级快链重。
- **在 worktree 里跑时说清哪条未受检**：`check-delivery` 的断言④ 数 worktree 数量，在 worktree 里必然红；那不是它坏了。此时传实际数量让①②③ 仍受检，并明说④未受检。

## Answer

已落地（2026-10-25）。走 §6 流程；spec、票、改动合成一个交付提交。

**首次跑就抓到一条真相**：`check-delivery` 在当前状态下是红的——但原因不是它坏了，而是断言④ 数 worktree 数量、而 ticket worktree 正开着。这件事值得记：**断言④ 是收尾后的判据，在工作期间必然红**。所以自检要区分「状态相关」与「写坏了」，不能一律当问题。修法是在非主 checkout 下传实际数量，并明说④未受检。

**探针**：`scripts/check-probe-tmp.mjs`（总是 `exit(1)`）→ 自检报「9 个门禁里 1 个是红的」并附它的最后一行输出；删除后恢复「8 个全绿」。验完即删，未入库。

**它接住的到底是哪一类**：门禁在真实状态下漂红。实测我那 4 次判据错里它能抓 2 次（计数棘轮、「只上树判据」那两次都是全程红）；用 `base` 而非 `tip` 那一次只在交付期误报，它抓不到。

**没做的另一半**：给每个门禁写 `--probe`（自造破坏、必须判红）。那是「永远绿」那一半，写在 spec 的 Out of Scope。
