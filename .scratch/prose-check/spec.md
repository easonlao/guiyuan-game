# Spec: 语句门禁——抓住「查找替换改坏」的句子 (prose-check)

## Problem Statement

2026-10-25 那轮文档清理里，我用查找替换一次改了几十个文件，改完只看了 diff 的开头和结尾。中间被改坏的句子没看见，事后靠人逐行找才清掉。四种实际损害：

| 损害 | 例子 |
|---|---|
| 括号里套括号 | 先查活/死参数清单（活/死参数普查报告（已删，见 git 历史）） |
| 相邻两对括号 | …归 burst-plus-two 平衡报告（已删，见 git 历史）（本文只引关键数字） |
| 汉字之间夹空格 | 取自候选搜索 候选搜索报告（已删，见 git 历史）/§4.5 |
| 吃掉章节号 | 只剩 `/§4.5`，前面的 `§4.1` 没了 |

人眼复查靠不住：那轮我是「批量替换 → 直接提交」，中间没跑过任何检查。

## 决定

1. **只查本次改动新增的行。** 怪句子一定是新引入的，老行不会凭空变质；全仓查会撞上故意的写法与合法嵌套（实测 7 处误报）。
2. **只查 `.md`。** 代码注释里汉字夹空格、括号跨行是正常写法（实测 `*.ts` / `*.mjs` 会多出 23 处误报）。
3. **四条规则一起跑。** 逐条实测：单条都漏，四条合起来才覆盖上面四种损害。
4. **围栏代码块不查，行尾 `prose-ok` 可豁免。**
5. **挂进 `check:quick`**（毫秒级）。提交前跑，正是能拦住的位置。

## Out of Scope

- 查代码文件（注释里的正常写法会误报，另有 review 兜）。
- 拦住「判据选错」那类错——它不是文本问题，四条规则都管不到。
- 自动修复：本门禁只报告，改法由人定。
