# 01: check:prose——四条规则只查改动的 Markdown 行

**Type:** task
**Blocked by:** None
**Status:** resolved
**Slice:** S1

**What to build:** `scripts/check-prose.mjs` + `npm run check:prose`，挂进 `check:quick`。

## 四条规则（逐条实测过覆盖范围）

| 规则 | 抓的损害 | 判据 |
|---|---|---|
| 括号不配对 | 少一个括号 | 同一行里 `（` 与 `）` 数量不等 |
| 汉字之间夹空格 | 替换留下多余空格 | 两个汉字之间有一个空格 |
| 括号里再套括号 | 整句被包了两层 | `（…（`，40 字以内 |
| 相邻两对括号 | 两个括注拼在一起 | `）` 后面紧跟 `（` |

单条都漏、四条合起来才全覆盖——所以四条一起跑。

## 范围（三条约束，都来自实测）

1. **只查 `git diff HEAD` 新增的 `.md` 行**：全仓查会撞上故意的排字（`docs/adr/0017` 的 `平衡 对 激进压制`）与合法嵌套，实测 7 处误报。怪句子只出现在新行上。
2. **不查代码文件**：`*.ts` / `*.mjs` 里汉字夹空格、括号跨行是正常写法，实测 23 处误报。
3. **围栏代码块不查**；行尾写 `prose-ok` 可豁免该行。

## Answer

已落地（2026-10-25）。走 §6 流程：`spec/prose-check` → `ticket/prose-check/01` → squash 回 spec → 切片验证 → 整理到 main。**spec、票、改动合成一个交付提交**——上一条规则就是这么来的（spec 的票据表声明了票而票面缺席，第一个提交会判红）。

**探针实测（三次，都在 ticket worktree 里跑）：**

| 探针 | 做法 | 结果 |
|---|---|---|
| 一 | 向一个已入库的 md 追加四行损害 | **判红 6 处**，文件:行号 + 规则名 + 原句都在 |
| 二 | 同样的损害行行尾加 `prose-ok` | 命中数不变（该行被跳过） |
| 三 | 同样的损害放进围栏代码块 | 命中数不变（代码块不查） |

**两条设计取舍**：

- 只报告不自动改。自动改写会重演「机械替换不复核」——正是本门禁要防的那件事。
- 划分只在改动行上判，不做全仓 lint。全仓跑会把老文档里合法的写法报成错，那种噪音会让人很快学会忽略这个门禁。

**没管到的**：这一票只管文本层。判据选错那类错（例如门禁该比内容却比了计数）与它无关，四条规则都碰不到。
