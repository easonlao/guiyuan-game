# 02: 护栏下界收紧 (Tighten the Guardrail Lower Bound)

**What to build:** 让归元率护栏带**本身**能拦住回退。

**背景：** 工单 06 按 spec 决策 13 重设了护栏带，归元率带为 `[0.86, 0.95]`。

但独立实测：把生产「进度定价」去掉后，归元率约 **88.4%**，**仍在带内**，该断言**通过**。也就是说这条带拦不住回退——真正拦住回退的是绊线、M1 基线与同文件里硬编码的分值断言。

带的下界 `0.86 = 锚点 90.40% − 约 4.4pp`，恰好把改动前的 88.4% 包了进去。

**要做的事：** 把归元率带下界从 0.86 收到 **0.88**（锚点 − 约 2.4pp），使改动前的 88.4% 落在带外。

**注意：** 收紧会带来抖动风险。必须复跑确认新带在固定种子下稳定，并在注释里写清锚点与理由。

**Blocked by:** None

**Status:** resolved

- [x] 归元率带下界 0.86 → 0.88；注释写清新锚点与理由。证据：`a4011e6`。**实际收到 0.89 而非 0.88——0.88 达不到本工单自己的验收标准，见下方「与原工单的偏离」。** 注释写明锚点口径（500 局平衡自对弈、`baseSeed` 默认 10000、`maxRounds` 默认 30 → 归元率 90.40%）、余量（锚点 − 1.4pp）与被否决的 0.88 及其理由。
- [x] 复核先手带是否也需要收紧（旧值是否落在 `[0.47, 0.54]` 内）。证据：`a4011e6`。复核结论：**旧值落在带内**——无进度定价时先手 51.20% ∈ `[0.47, 0.54]`，该带同样拦不住回退。故上界 `0.54 → 0.51`（锚点 50.40% + 0.6pp），下界 0.47 不变；注释说明 0.6pp 余量偏薄是有意为之（回退幅度只有 0.8pp，不收紧就抓不到）。
- [x] 实测：去掉生产「进度定价」后，**护栏带断言本身**必须变红。证据：`a4011e6` 红探针——把 `src/core/logic/ScoreCalculator.ts:119` 的 `ATTACK_PROGRESS_SCALE` 置为 `undefined` 后，`tests/core/ai-evaluator-benchmark-guardrails.test.ts` 失败：`expected 0.884 to be greater than or equal to 0.89`；合并后于集成分支 `864cadf` 复跑（`48428346` 合并代理），共享谓词报出两条违规：`{actual: 0.884, bound: "guiYuanRate.min", boundValue: 0.89}` 与 `{actual: 0.512, bound: "p1WinRate.max", boundValue: 0.51}`。探针已还原，`src/core/logic/` 在集成分支上逐字节未改。
  - 陷阱已记录：live 测试用的是 `balancedStrategy`（预构建 `DecisionStrategy`，自带绑定了生产 `POINTS_CONFIG` 的估值器），传 `scoreConfig` 到不了它——所以红探针必须改生产配置本身，不能靠注入。
- [x] 固定种子下复跑确认新带不抖。证据：`a4011e6`，连跑 3 次得逐字节相同的 `0.904 / 0.504`（堆内存 3.02/2.98/3.52MB，天然带噪声，已排除）。判定确定性、无运行间抖动。
- [x] 测试全绿。证据：集成分支 `864cadf` 上 `npm test` 693/693、38 文件全绿；`npm run typecheck`、`npm run lint`、`npm run check:deps` 全绿。

## 与原工单的偏离（已复核，非遗漏）

1. **0.88 是算术错误，改为 0.89。** 工单写「把下界收到 0.88……使改动前的 88.4% 落在带外」，但断言是 `toBeGreaterThanOrEqual(下界)`，实测值 `0.884 ≥ 0.88` 仍然**通过**——工单自己的验收标准「去掉生产进度定价后护栏带断言本身必须变红」在 0.88 下**不可能达成**。以工单声明的**意图**（让 88.4% 落在带外）为准，取 `0.89 = 锚点 90.40% − 1.4pp`，它同时满足「锚点在带内」与「回退在带外」。代码注释与 ADR 0011 都显式记下「勿改回 0.88」及其理由，防止后来者「修正」回去。
2. **先手带也收紧了（工单只说复核）。** 工单给出的复核判据是「旧值是否落在 `[0.47, 0.54]` 内」；答案是落在内（51.20%），故按判据收紧到 `[0.47, 0.51]`。
3. **同源的第二份带在工单范围外，另立工单 03 处理。** 侦察发现 `src/core/headless/CandidateValidation.ts:78-84` 另有一份带（`[0.75, 0.95]` / `[0.45, 0.55]`），工单 06 从未更新它——即本工单要修的缺陷在候选验证 CLI 上的完整复现。见工单 03。
