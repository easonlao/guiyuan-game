# 05: 重做 check:delivery 断言③——用树判据，不用计数棘轮

**Type:** task
**Blocked by:** None
**Status:** ready-for-agent
**Slice:** S4

**What to build:** 把 `scripts/check-delivery.mjs` 的断言③（「无新增孤儿提交」）从**计数棘轮**改成**树判据**。改完删掉基线常量。

## 为什么必须改（实测证据）

计数棘轮**按构造每轮必红**。squash + rebase 的流程每轮都抛弃原始提交；分支一删，它们就变成不可达。所以每交付一轮，计数必然上涨：

| 时点 | 不可达提交数 | 事件 |
|---|---|---|
| 2026-10-25 基线 | 479 | 线性化重写后的实测值 |
| S1 交付 + 收尾 | **482**（+3） | 弃掉 `1066fb2`、`02bd21c`、`3979c3b`（S1 的 spec / ticket / 快照提交） |
| S2 交付 + 收尾 | **484**（+5） | 同上，多三条本轮的 spec / ticket / delivery 提交 |

判红的那些提交全是**交付残渣**，内容早已在 main 里。一个每次都红的门禁比没有门禁更糟：没人会再跑它。按脚本自带的建议「确实作废才重钉基线」，等于每轮手工重钉一次——那这条断言就没在拦住任何东西。

## 改法：问「有没有 main 里没有的孤儿工作」

真问题不是「不可达提交有几个」，是「**有没有内容不在 main 里的不可达提交**」。但只靠树判据**太宽**——二分二版实测踩过（见下）。最终口径是两个条件与：

```
不可达提交中，author date 晚于水位线（WATERMARK = 2026-10-20）
且 树不在 main 的树集合里  →  报红
```

1. `git fsck --unreachable --no-reflogs` 取不可达提交。
2. `git log --format=%T <base> | sort -u` 取 main 的树集合（`<base>` 默认 `origin/main`，与断言① 同源）。
3. 逐条过两道滤：日期早于水位线的放过；树在集合里的放过。
4. 剩下的报红并列出提交本身。

两个条件各管一头：**树判据**滤掉 squash/rebase 的交付残渣（它们的树就是 main 里那些交付提交的树）；**水位线**滤掉线性化之前的 30 个历史中间态。这样没有跑步机——不像计数棘轮那样每轮要手工重钉。

### 第一版判据（只有树判据）实测不成立：34 个命中，33 个是假阳性

| author 日期 | 个数 | 性质 |
|---|---|---|

| 2026-10-09 | 14 | 同上（含 `Checkpoint` 与 `WIP on …` 的 stash 残骸） |
| 2026-10-10～13 | 15 | 同上（分支中间态，工作已由别的路径交付） |

| **2026-10-24** | **1** | **`ccc3886`——唯一的真孤儿** |

根因：分支的**中间态**本来就从未作为完整状态存在于 main，但它的工作早已交付。所以「树不在 main 里」单用不行，需要水位线。

## 实现要点

- **别用 patch-id 代替树判据。** squash 与 rebase 都会改 patch-id，而树不变——`ccc3886` 那类「分支整条没合」用两者都能抓，但正常交付会用 patch-id 误报。树是这里唯一稳的量。
- 报红时打印**提交列表本身**，不要只给个数。旧口径打了计数，看的人还得自己去翻 484 个。
- 顺带把这条教训写进脚本头注：**对账与验收优先用内容判据（树、对象、逐字节），不用计数或结构判据。** 这是本路线第二次撞上同一类问题——上一次是收尾删分支：`git branch -d` 用「是否 main 的祖先」这个结构判据，在 squash + rebase 下永远通不过（见 §6.3.7）。
- 本票改的是 `scripts/`，不在快速通道内，按 §6 走 spec 分支 + ticket 分支。

### 三种情形实测

| 情形 | 结果 |
|---|---|
| 正例：当前 main（483 个不可达提交，全被两道滤放过） | 退出 0 |
| 破坏例：临时 clone 里造一个游离提交（树含 `probe-orphan.txt`，author date 今天） | **判红**，只列 1 个：`f1badcd 2026-10-25 probe: orphan work never merged` |
| 树判据生效：再造一个「树与 main tip 相同」的游离提交 | 仍只列那 1 个——同树的被放过 |
| 水位线生效：`--watermark 2026-12-31` | 退出 0，孤儿被日期滤掉 |

破坏例在**临时 clone** 里做，不在本仓：在本仓造游离提交会永久留下一个真会报红的对象（新判据按内容报红，不按计数，gc 之前一直在）。

### 与旧口径的差别

旧：不可达提交数 > 479 → 红。squash + rebase 每轮都抛弃原始提交，所以每轮必红（实测 479 → 482 → 484），只能靠手工重钉基线绕过。

新：树不在 main 的树集合里 **且** author date 晚于水位线 → 红。交付残渣被树判据滤掉，历史中间态被水位线滤掉，两边都不随交付轮次变化，没有跑步机。

### 第二个缺陷：交付期误报自己的提交（同日修）

第一版用 `<base>`（默认 `origin/main`）的树集合做比对。交付整理时，本轮自己的 spec / ticket 提交本来就还没进 main，于是被判成孤儿——实测在 `delivery/delivery-protocol` 上报了 2 个误报（`be35381`、`ef0ddb0`，都是本轮 amend / rebase 弃掉的等价提交）。

修法：树集合取 **`<tip>` 的全部提交**，而不是 `<base>`。交付分支从基点长出来，所以 `tip` 的可达集天然包含 `base`；同时把「本轮正在交付的内容」也纳进来，交付期不再自报。

对应地，错误信息从「树不在 `<base>` 里」改成「树不在 `<tip>` 的交付范围内」。

### 第三个缺陷：amend 也弃提交，且这条无法用范围判据解决

`amend` 每次都造一个新树，旧版本的树永远不会出现在交付里。本票自己 amend 两次，就积了 3 个旧版本（`7a9e9ef`、`be35381`、`ef0ddb0`），全被树判据报成孤儿。

试过再加一条「孤儿与 tip 的差异文件是否全在本次交付改动集里」——**不成立**：交付合入后 `base..tip` 为空，交付改动集为空，判据立刻失效。它只在交付窗口内成立，不能当常设判据。

**最终解法：把瞬态垃圾交给 `git gc`，断言只管 gc 之后还活着的东西。**

- 交付收尾顺序变成：ff 合入 → 删 worktree / 分支 → **`git gc --prune=now`** → `npm run check:delivery`。
- gc 之后不可达提交归零，被 amend 弃掉的旧版本、被 squash / rebase 弃掉的原始提交、线性化之前的历史中间态一起消失。断言从此没有跑步机。
- **代价**：gc 是不可恢复的。所以要保存的东西必须先打 tag——`ccc3886` 已于本票之前打 `archive/ccc3886-frontend-full-experience`，gc 后实测仍在（`git cat-file -t ccc3886` → `commit`）。
- **能力验证**：gc 之后再造一个孤儿，断言立刻判红（实测 `6fa5486` 被抓出）。所以它没有退化成永远通过。

这条也解释了 tag 的真正用途：**tag 是「gc 不该回收」的唯一标记**。归档不是情怀，是给 gc 的豁免名单。
