## D1 squash 后的 body 口径

**现状**：你的原文第 5 步已经定了 squash（「把这张票 squash 合入 spec，形成一个带票据编号的提交」），所以这里不是二选一，只剩一件事要定——**squash 之后 body 里必须留住什么**。

**为什么重要**：本仓库的提交 body 是主要资产（提交「docs: 清掉三处「CI 跑突变测试」的过期表述」逐条列「没动的地方和理由」）。squash 会丢掉票内多次本地提交的推理链。

**选项：**
- A. body 写：切片名 + 票号 + 该票的关键取舍（被否决的做法及原因）+ 验证命令。推荐。
- B. body 只写：切片名 + 票号 + 验证命令。取舍靠 `.scratch` 里的票面承载。
- C. 保留票内提交（等价于放弃 squash）→ 与 spec 决定 1 的线性要求不冲突，但交付提交数会膨胀，切片边界变模糊。

**推荐 A**，理由：`.scratch` 里的票面在收尾时会被归档甚至删除（见 doc-dedup 施工图第 3 步），body 是唯一能跟着代码走的地方。

## D2 快速通道的画线

**为什么必须定：** 最近 25 条提交里 20 条以上是 `docs:` / `chore:` / `ci:` 的单行修正。这些走完整流程（spec → ticket → squash → 切片验证 → 整理 → `rebase --exec`）不成立。不定线，流程会被绕过。

**选项：**
- A. 同时满足三条即可直推 main，仍跑 `npm run verify`：① 不改 `src/`；② 不动依赖（`package.json` / `package-lock.json`）；③ 改动文件 ≤ 3 个。
- B. 只按路径判：**只**改 `docs/`、`.scratch/`、根目录 `*.md` 时直推；`.github/`、`scripts/`、`tests/` 一律走流程。
- C. 不设快速通道，但允许「单票即切片」的轻量 spec。

**推荐 A + B 的交集**：路径在白名单内 **且** 文件数 ≤ 3。白名单要排除 `scripts/`、`.github/`、`tests/`——这三处改错了会静默降低门禁强度。

## D3 `minigame/game.js` 在切片重排时的处理

**为什么是问题：** 入库产物的逐字节对账（`npm run check:artifact`）意味着任何改 `src/` 的提交都必须自带重建后的 6080 行产物。按切片依赖顺序重排提交时，每一步都会在产物上冲突。

**选项：**
- A. 每重排一个提交，解冲突后重跑 `npm run build:minigame` 并 `git commit --amend`，然后 `npm run verify`。产物始终与源码同提交。推荐。
- B. 产物从切片提交里摘出来，整理阶段末尾统一打一次。
- C. 产物不入库（会破 ADR 0014，等于重开一个已决问题）。

**推荐 A**，理由：它保住「每个交付提交自己就能过 verify」这条性质，而这条正是 `rebase --exec` 的前提。代价是整理阶段每步多跑一次构建（实测构建在秒级）。
